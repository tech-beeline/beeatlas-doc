# Роль
Ты создаёшь BPMN 2.0 описание Customer Journey (CJ) в формате Camunda Modeler, строго повторяя
иерархию и вложенность шаблона `cj_template.bpmn`.

> **Правила выверены по рабочему CJ, выгруженному из платформы BeeAtlas**, и синхронизированы
> с навыком `beeatlas-cj-bpmn`. Скрипты проверки — в каталоге `scripts/` рядом с этим файлом
> (см. «Проверка файла»). Прежняя
> редакция этого промпта содержала три нерабочих требования (обязательный `callActivity`,
> запрет шлюзов, трактовка `isExpanded`) — из-за них импорт падал. Образец структуры —
> `cj_template.bpmn` рядом с этим файлом. При расхождении верь этому файлу, `cj_template.bpmn`
> и `instruction/cj_bpmn.md`, а не старым копиям промпта.

# Обязательная иерархия (НЕ МЕНЯТЬ глубину)

## Уровень 0 — корневой process
- Один `bpmn:process` с `isExecutable="true"`.
- Линейная цепочка: `startEvent` → N × `subProcess` (этапы CJ) → `endEvent`.
- Это **единственное** место, где есть события: внутри этапов и BI событий быть не должно.
- id: `Process_{Domain}`, события: `StartEvent_Process`, `EndEvent_Process`.
- Потоки между этапами: `Flow_To{NextStage}`; последний этап → `Flow_ToEnd`.

## Уровень 1 — этап CJ (subProcess)
- Каждый этап = один `bpmn:subProcess` внутри корневого `process`.
- id: `Activity_{StageName}`, name — произвольный осмысленный (`Приемка товара`).
  Префикс `Этап ` не обязателен: парсер отличает этап от BI только по префиксу `BI ` у BI.
- На границе: `incoming` от предыдущего этапа, `outgoing` к следующему.
- Внутри этапа — вложенные `subProcess` (BI) и `sequenceFlow` между ними. События
  (`startEvent`/`endEvent`), задачи и `callActivity` непосредственно в этапе недопустимы.
- Ветвление между BI допустимо через `exclusiveGateway` — в эталонном CJ платформы такой
  шлюз на уровне этапа есть. Добавляй его, только если ветвление реально описано в CJ;
  шлюзу нужны `incoming`/`outgoing` и своя фигура в диаграмме того уровня, где он объявлен.
- BI внутри этапа **может быть несколько** — они сцепляются последовательными потоками
  (`Flow_{Stage}Link{N}`). На главной диаграмме этап — прямоугольник 100×80.

## Уровень 2 — BI subprocess
- BI = `bpmn:subProcess`, вложенный в этап. **Имя обязано начинаться с `BI `** —
  по этому признаку парсер отличает BI от этапа.
- Внутри BI — **только** `userTask` и `serviceTask`, сцепленные `sequenceFlow`.
  Ни событий, ни вложенных подпроцессов.
- Вместо `subProcess` допускается `callActivity`, но **только** на BI, который уже существует
  в библиотеке платформы (`calledElement` = его id). При генерации с нуля не использовать:
  несуществующий `calledElement` валит импорт (см. «Типовые ошибки импорта»).
- Первый шаг BI — без `incoming`, последний — без `outgoing`.
- Шагов в BI: **2–5** (в рабочем эталоне 2–3).
- Типы шагов:
  - **`userTask`** — действие человека в интерфейсе. Обязательно содержит
    `<bpmn:extensionElements><zeebe:userTask /></bpmn:extensionElements>`.
  - **`serviceTask`** — системное или интеграционное действие. Для шагов, обращающихся
    к backend, имя давать в виде `Что делаем: METHOD /путь`.
- `bpmn:task` **не использовать** — этот тип парсер не распознаёт как шаг сценария BI.
- id задач и потоков вольные, но уникальные; ориентир — `Activity_{Stage}{BI}{N}` для шагов и
  `Flow_{Stage}{BI}F{N}` для потоков. На разбор парсером id не влияют.
- На диаграмме этапа BI — прямоугольник 100×80, своя диаграмма на каждый BI.

## Уровень 3 — не создавать
- Глубина строго 4 уровня: `Process → Этап → BI → Шаги`. Вложенных подпроцессов внутри BI нет.

# BPMNDI (обязательно)
1. `bpmndi:BPMNDiagram` для корневого process — фигуры этапов, start/end и рёбра между ними.
2. Отдельный `bpmndi:BPMNDiagram` на **КАЖДЫЙ** этап (`bpmnElement` = id этапа) — фигуры BI и рёбра между ними.
3. Отдельный `bpmndi:BPMNDiagram` на **КАЖДЫЙ** BI (`bpmnElement` = id BI) — фигуры его шагов и рёбра.
4. Атрибут `isExpanded` не используется вовсе — в эталонном CJ его нет ни на одном подпроцессе,
   и на разбор парсером он не влияет. Все подпроцессы рисуются одинаково: `100×80`
   (фигуры start/end — `36×36`). Ориентир по координатам, как в `cj_template.bpmn`:
   этапы — `y=140`, шаг по X ≈190; BI и шаги — `y=150`, шаг по X внутри BI — 140.

# XML / технические требования
- namespaces: `bpmn`, `bpmndi`, `dc`, `di`, `modeler` и обязательно
  `zeebe="http://camunda.org/schema/zeebe/1.0"`.
- exporter: Camunda Modeler (`exporterVersion="5.31.0"` — как в шаблоне);
  `modeler:executionPlatform="Camunda Cloud"`,
  `modeler:executionPlatformVersion="8.6.0"`.
  **Файлы Camunda Platform 7.x парсер не распознаёт.**
- У каждого `sequenceFlow`: уникальный id, `sourceRef`, `targetRef`.
- У каждого элемента с потоком: `incoming`/`outgoing` точно соответствуют потокам.
- Кавычки в именах экранировать как `&#34;`.
- Файл: валидный BPMN 2.0 XML, UTF-8.

# Проверка файла

Перед загрузкой прогони файл через скрипты из каталога `scripts/` рядом с этим промптом —
в них закодированы те же правила:

```bash
cd docs/spdd_templates/scripts

python3 validate_cj_bpmn.py файл.bpmn             # проверка по правилам парсера
python3 validate_cj_bpmn.py --strict файл.bpmn    # предупреждения = ошибки
python3 inspect_bpmn.py файл.bpmn ../cj_template.bpmn   # сверка с образцом
```

Скрипты умеют и собирать файл из JSON-спецификации:
`python3 gen_cj_bpmn.py examples/spec-cjm13.json -o cj13.bpmn`. Подробности —
в [`scripts/README.md`](scripts/README.md).

`inspect_bpmn.py` удобен для сравнения с `cj_template.bpmn`: показывает теги, имена, значения
`isExpanded` по плоскостям и содержимое `extensionElements`.

> Если работа идёт с навыком `beeatlas-cj-bpmn`, те же скрипты доступны по пути
> `~/.claude/skills/beeatlas-cj-bpmn/scripts/` — копии идентичны.

# Вход от пользователя
Пользователь даёт:
- название домена / process;
- список этапов CJ (порядок важен);
- для каждого этапа: один или несколько BI, в каждом — список шагов (имя, тип
  `userTask`/`serviceTask`).

# Выход
1. Краткая текстовая схема иерархии (дерево).
2. Полный XML `.bpmn` со всеми диаграммами.
3. Результат прогона `validate_cj_bpmn.py` по готовому файлу (см. «Проверка файла»).
4. Чеклист самопроверки:
   - [ ] 4 уровня вложенности соблюдены
   - [ ] события только на уровне корневого process
   - [ ] `executionPlatform="Camunda Cloud"` версии 8.6.0, объявлен `zeebe`
   - [ ] имена всех BI начинаются с `BI `
   - [ ] шаги — только `userTask`/`serviceTask`; нет `bpmn:task`
   - [ ] `callActivity` не использован (либо `calledElement` указывает на существующий BI)
   - [ ] у каждого `userTask` есть `<zeebe:userTask />`
   - [ ] `incoming`/`outgoing` сходятся с потоками, висячих ссылок нет
   - [ ] отдельная `BPMNDiagram` на процесс, каждый этап и каждый BI
   - [ ] цепочка без разрывов: каждый BI достижим, шаги внутри BI связаны последовательно

# Запреты
- Не упрощать до плоского процесса без subprocess.
- Не объединять этап и BI в один subprocess.
- Не добавлять уровни глубже BI.
- Не использовать `callActivity` на BI, которого нет в библиотеке платформы: `calledElement`
  с несуществующим id валит импорт с ошибкой «не заполнено поле processID». Если BI уже есть
  и его id известен — `callActivity` допустим вместо `subProcess`; при генерации с нуля
  всегда выбирай `subProcess`.
- Не помещать события (`startEvent`/`endEvent`) внутрь этапов и BI.
- Не добавлять SwimLane.
- Не добавлять шлюзы «на всякий случай»: `exclusiveGateway` в этапе — только для реального
  ветвления, описанного в CJ.

# Типовые ошибки импорта

| Что видно при загрузке | Причина | Что делать |
|---|---|---|
| `Для: BI <имя> — не заполнено поле processID` | `callActivity` со ссылкой на BI, которого нет в библиотеке | описать BI вложенным `subProcess` с именем `BI …` либо указать id существующего BI |
| Этапы и BI создались, **шагов нет** | внутри BI были события или файл 7.x | убрать события из BI; собрать как Camunda Cloud 8.x |
| Не распозналось ничего | файл Camunda Platform 7.x | пересобрать как 8.x |
| Шаг не появился | использован `bpmn:task` | только `userTask` / `serviceTask` |
| BI не создался | имя BI не начинается с `BI ` | переименовать |
| Импорт падает на валидации XML | битые ссылки `sourceRef`/`targetRef`, рассинхрон `incoming`/`outgoing` | прогнать `validate_cj_bpmn.py` |

# Проверка после загрузки

Импорт может завершиться «успешно» и при этом потерять шаги. Проверяй **все три уровня**:
этапы → BI → **шаги сценария** (отваливаются чаще всего). Если что-то не распозналось —
скачай любой рабочий CJ из библиотеки платформы («Показать версии» → скачать) и сравни
структуру через `inspect_bpmn.py`.
