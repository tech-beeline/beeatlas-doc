# Описание проверок архитектуры (Fitness Functions)

---

## 1. Контекстные диаграммы 

### CTX.01 — Создана диаграмма контекста
- **Описание:** В модели должна быть хотя бы одна контекстная диаграмма (System Context View).
- **Успех:** Найдена хотя бы одна `systemContextView` для целевой системы.
- **Неуспех:** Контекстных диаграмм нет.

### CTX.02 — Все связи на диаграмме контекста должны быть подписаны
- **Описание:** У каждой связи (relationship) на контекстной диаграмме должно быть заполнено поле `description`.
- **Успех:** Все связи имеют описание.
- **Неуспех:** Есть связи без описания.

### CTX.03 — Все связи на диаграмме контекста должны иметь технологию взаимодействия
- **Описание:** У каждой связи на контекстной диаграмме должно быть указано поле `technology`.
- **Успех:** Все связи имеют технологию.
- **Неуспех:** Есть связи без технологии.

---

## 2. Технические возможности 

### CPB.01 — Определены технические возможности продукта
- **Описание:** У продукта должны быть определены технические возможности (TC) — в Structurizr или в landscape (BeeAtlas).
- **Успех:** Найдены capability-компоненты в модели или опубликованные TC в landscape.
- **Неуспех:** Нет ни capability в Structurizr, ни в landscape.

### CPB.02 — Для всех внешних интеграций определены TC
- **Описание:** Контейнеры, участвующие во внешних интеграциях (входящие/исходящие связи с внешними системами), должны иметь TC.
- **Успех:** У всех таких контейнеров есть capability-компоненты.
- **Неуспех:** Есть контейнеры с внешними связями без TC.

### CPB.03 — Есть capability в Structurizr
- **Описание:** В модели Structurizr должны быть описаны technical capability с полями `code` и `parents`.
- **Успех:** Найдены capability-компоненты с полным описанием.
- **Неуспех:** Нет описанных TC в Structurizr.

### CPB.04 — Позиционирование в ФДМ выполнено корректно
- **Описание:** TC не должны быть спозиционированы в группах `dmn.*` или `grp.*` (неверное позиционирование в ФДМ).
- **Успех:** У всех TC корректные родительские группы.
- **Неуспех:** Хотя бы одна TC имеет родителей `dmn.*` или `grp.*`.

### CPB.05 — Качество описания TC продукта в ФДМ соответствует методике
- **Описание:** Оценка качества описания TC по данным из БД BeeAtlas (критерий 101). Проверка не пройдена, если есть TC с оценкой 0–2.
- **Зависимости:** Переменные окружения `FDMDB_SERVER`, `FDMDB_DB`, `FDMDB_USERNAME`, `FDMDB_PASS`.
- **Успех:** Нет TC с оценкой 0–2.
- **Неуспех:** Есть TC с оценкой 0–2.

## 3. Технологии 

### TECH.01 — Все технологии продукта есть в техрадаре
- **Описание:** Все технологии контейнеров и связей должны присутствовать в техрадаре.
- **Успех:** Все технологии найдены в техрадаре.
- **Неуспех:** Есть технологии, отсутствующие в техрадаре.

### TECH.02 — В продукте нет технологий в статусе HOLD
- **Описание:** Не допускается использование технологий со статусом HOLD в техрадаре.
- **Успех:** Нет технологий в статусе HOLD.
- **Неуспех:** Обнаружены технологии в статусе HOLD.

### TECH.03 — У всех контейнеров есть технологии
- **Описание:** У каждого контейнера (кроме из landscape) должно быть указано поле `technology`.
- **Успех:** У всех контейнеров указана технология.
- **Неуспех:** Есть контейнеры без технологии.

### TECH.04 — Приложение не использует протоколов в статусе hold
- **Описание:** Связи между контейнерами не должны использовать протоколы в статусе HOLD.
- **Успех:** Нет связей с протоколами в статусе HOLD.
- **Неуспех:** Есть связи с протоколами в статусе HOLD.

### TECH.05 — У всех взаимодействий указаны протоколы из техрадара
- **Описание:** Технологии взаимодействия (протоколы) должны быть из техрадара.
- **Успех:** Все протоколы связей есть в техрадаре.
- **Неуспех:** Есть взаимодействия с протоколами не из техрадара.

### TECH.06 — Технологии из мониторинга продуктивной среды и Git описаны в архитектуре
- **Описание:** Технологии, обнаруженные мониторингом и GitLab, должны быть отражены в архитектурной модели.
- **Исключения:** HTML, CSS, SSH 2.0, Docker, Alpine Linux, HCL, Groovy, Jinja, Prometheus.
- **Успех:** Нет расхождений между мониторингом и архитектурой.
- **Неуспех:** Есть технологии из мониторинга, не описанные в архитектуре.

## 4. Динамические диаграммы 

### SQ.01 — Для всех technical capability указаны sequence
- **Описание:** Для каждой технической возможности должна быть динамическая диаграмма (dynamic view).
- **Успех:** Для всех TC найдены соответствующие sequence-диаграммы.
- **Неуспех:** Есть TC без sequence-диаграмм или TC не определены.

### SQ.02 — Все вызовы содержат HTTP запросы
- **Описание:** В sequence-диаграммах вызовы с REST-технологиями (HTTP/HTTPS/REST) должны иметь описание в формате `GET/POST/PUT/DELETE/PATCH ...`.
- **Успех:** Все HTTP-вызовы имеют корректный формат.
- **Неуспех:** Есть REST-вызовы без корректного HTTP-endpoint в описании.

## 5. Диаграммы развёртывания 

### DEP.01 — Наличие хотя бы одного Deployment Environment
- **Описание:** В модели должны быть deployment nodes с указанием окружения (`environment`).
- **Успех:** Найден хотя бы один deployment environment.
- **Неуспех:** Нет deployment environments.

### DEP.02 — Наличие хотя бы одной Deployment диаграммы
- **Описание:** Должна быть хотя бы одна deployment view.
- **Успех:** Найдена хотя бы одна deployment-диаграмма.
- **Неуспех:** Нет deployment-диаграмм.

### DEP.03 — Deployment environment соответствует CMDB
- **Описание:** Узлы развёртывания (VM, k8s namespace) должны соответствовать данным CMDB.
- **Успех:** Все узлы найдены в CMDB.
- **Неуспех:** Есть узлы, не найденные в CMDB.

### DEP.04 — Правильно задана макросегментация
- **Статус:** Описана в assessments, логика не реализована (TODO).

## 6. Контейнерная модель 

### CNT.01 — Наличие в модели контейнеров для системы
- **Описание:** У целевой системы должны быть контейнеры.
- **Успех:** Найдены контейнеры.
- **Неуспех:** Система не содержит контейнеров.

### CNT.02 — Наличие хотя бы одной диаграммы контейнеров
- **Описание:** Должна быть хотя бы одна container view для системы.
- **Успех:** Найдена контейнерная диаграмма.
- **Неуспех:** Контейнерной диаграммы нет.

### CNT.03 — Все вызовы между контейнерами имеют технологию
- **Описание:** У каждой связи между контейнерами должно быть указано поле `technology`.
- **Успех:** Все связи имеют технологии.
- **Неуспех:** Есть связи без технологии.

### GIT.01 — Наличие в модели git репозитория
- **Описание:** Контейнеры (кроме инфраструктурных и external) должны иметь URL с git/nexus/harbor.
- **Успех:** У всех прикладных контейнеров есть репозиторий.
- **Неуспех:** Есть контейнеры без git-репозитория.

## 8. API и SLA

### API.01 — У приложения есть опубликованные API
- **Описание:** У приложения должны быть API-интерфейсы с методами (из спецификаций OpenAPI/WSDL/Proto).
- **Примечание:** При локальных спецификациях проверки API пропускаются.
- **Успех:** Найдены интерфейсы с методами.
- **Неуспех:** Нет ни одного API.

### API.02 — Для некоторых методов определен SLA
- **Описание:** Хотя бы для части методов API должны быть заданы SLA (rps, latency, error_rate) через properties или интеграцию.
- **Успех:** Найден хотя бы один метод с SLA.
- **Неуспех:** SLA не определен ни для одного метода.

### API.03 — Для всех TC есть спецификация
- **Описание:** Интерфейсы с привязкой к TC (`implements`) должны иметь спецификацию (`api_url`).
- **Успех:** У всех интерфейсов с TC есть спецификация.
- **Неуспех:** Есть интерфейсы с TC без спецификации.
