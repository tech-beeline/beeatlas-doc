# Описание проверок архитектуры (Fitness Functions)

**Фитнес-функция (FF)** — автоматическая проверка архитектуры приложения. У каждой функции есть уникальный код, название, тип выполнения (скрипт, синхронный или асинхронный метод) и статус. Результат — «пройдена / не пройдена» с детализацией по объектам проверки.

Проверки выполняет сервис `structurizr-backend`. Часть функций входит в **агрегированный прогон** при публикации архитектуры, часть доступна **только отдельными запросами** — это указано в описании функции. Актуальный состав каталога и статусы — на портале в разделе [Управление фитнес-функциями](beeatlas-docs/admin/fitness_functions.md) и на вкладке приложения [«Фитнес-функции»](beeatlas-docs/models/apps.md#вкладка-фитнес-функции).

---

## 1. Проверки и триггеры

Каталог делится на два вида функций:

| Вид | Признак в карточке | Что делает | Результат на карточке приложения |
|-----|--------------------|------------|----------------------------------|
| **Проверка** | Триггер = Нет | Проверяет соответствие архитектуры правилу | «Успешно» / «Ошибка» |
| **Триггер** | Триггер = Да | Контекстная оценка: выявляет свойства приложения, влияющие на применение к нему определённых правил | «Обнаружено» / «Не обнаружено» |

**Триггер сам по себе не нарушает правило.** Он отвечает на вопрос «применимо ли правило к этому приложению»: использует ли приложение PostgreSQL, Kafka или Redis, есть ли у него UI-контейнеры и персоны пользователей, насколько оно критично. По результату триггера включаются зависимые проверки — в том числе через поле **«Применимость»**: фитнес-функция запускается только для продуктов, где пройдены выбранные функции.

### 1.1. Триггеры

| Код | Название | Тип | Статус | Что выявляет |
|-----|----------|-----|--------|--------------|
| `EXT-INET-01` | Приложение доступно из внешнего сегмента сети интернет | Script | Trial | Доступно ли приложение из внешнего сегмента |
| `CX.01` | Существует Person со связью с системой | Синхронный метод | Trial | Есть ли в модели пользователь (Person), связанный с системой или её контейнерами |
| `FF.TECH.POSTGRES` | Использование СУБД Postgres в PROD-окружении | Script | Trial | Используется ли PostgreSQL в продуктивной среде (по DSL) |
| `FF.TECH.REDIS` | Использование СУБД Redis в PROD-окружении | Script | Trial | Используется ли Redis в продуктивной среде (по DSL) |
| `ADR-02` | Наличие ADR по реализации НФТ приложения | Асинхронный метод | Trial | Описывают ли ADR приложения назначенные ему НФТ. Доступен только отдельным эндпоинтом `POST /api/v1/ff/adr02`, в агрегат не входит |
| `PG.01` | Наличие базы данных PostgreSQL у критичного приложения | Синхронный метод | Trial | Критично ли приложение (критичность 0–3) и есть ли у него PostgreSQL. Доступен только отдельным эндпоинтом `POST /api/v1/ff/pg01`, в агрегат не входит |

### 1.2. Где выполняются проверки

| Способ запуска | Что входит |
|----------------|------------|
| **Агрегированный прогон** `POST /api/v1/fitness-function/local/{docId}` | `CTX.01–03`, `CPB.01–05`, `TECH.01–06`, `SQ.01–02`, `DEP.01–03`, `CNT.01–02`, `GIT.01`, `ADR.01`, `API.01–02` — 25 кодов. Тот же набор публикуется через `/api/v1/workspace/{docId}/fdm` и `/api/v1/dsl2fdm` |
| **Отдельные эндпоинты** `/api/v1/ff/*` | `CX.01`, `CX.03`, `DEP.04`, `ADR.02`, `PG.01`, а также проверки связей (`REL-LEGACY-01`, `MAPIC-VALIDATE-RELATION-01`), AI-проверки и проверки БД контейнеров — в агрегат не входят |

### 1.3. Структура результата

Каждая проверка возвращает `FitnessStatus`:

| Поле | Описание |
|------|----------|
| `code` | Код проверки (например, `CTX.01`) |
| `isCheck` | `true` — проверка пройдена, `false` — не пройдена |
| `assessmentDescription` | Описание критерия |
| `resultDetails` | Детали результата (HTML) |
| `assessmentObjects` | Объекты для детализации: найденные и проблемные |

При публикации архитектуры проверки выполняются по порядку: контекст → технические возможности → технологии → динамические диаграммы → развёртывание → контейнеры и Git → ADR → API.

> **Состав документа:** описаны только функции в статусах **Adopt** и **Trial**. Функции в статусе Test в документ не включены.

> **Изменения состава каталога:** проверки `SEC.01` (интеграция с IDM) и `PAT.01` удалены без замены. `DEP.04` — заглушка, логика не реализована.

## 2. Контекстные диаграммы

### CTX.01 — Создана диаграмма контекста

- **Статус:** Trial.

- **Описание:** в модели должна быть хотя бы одна контекстная диаграмма (System Context View).
- **Успех:** найдена хотя бы одна `systemContextView` для целевой системы.
- **Неуспех:** контекстных диаграмм нет.
- **Доступность:** агрегированный прогон.

### CTX.02 — Все связи на диаграмме контекста подписаны

- **Статус:** Trial.

- **Описание:** у каждой связи на контекстной диаграмме должно быть заполнено поле `description`.
- **Успех:** все связи имеют описание.
- **Неуспех:** есть связи без описания.
- **Доступность:** агрегированный прогон.

### CTX.03 — Все связи на диаграмме контекста имеют технологию

- **Статус:** Trial.

- **Описание:** у каждой связи на контекстной диаграмме должно быть указано поле `technology`.
- **Успех:** все связи имеют технологию.
- **Неуспех:** есть связи без технологии.
- **Доступность:** агрегированный прогон.

## 3. Технические возможности (TC)

### CPB.01 — Технические возможности продукта определены

- **Статус:** Adopt.

- **Описание:** у продукта должны быть определены технические возможности (TC) — в Structurizr или в ландшафте BeeAtlas.
- **Успех:** найдены capability-компоненты в модели или опубликованные TC в ландшафте.
- **Неуспех:** TC нет ни в модели, ни в ландшафте.
- **Доступность:** агрегированный прогон.

### CPB.02 — Для всех внешних интеграций определены TC

- **Статус:** Adopt.

- **Описание:** контейнеры, участвующие во внешних интеграциях (входящие и исходящие связи с внешними системами), должны иметь TC.
- **Успех:** у всех таких контейнеров есть capability-компоненты.
- **Неуспех:** есть контейнеры с внешними связями без TC.
- **Доступность:** агрегированный прогон.

### CPB.03 — TC описаны в Structurizr

- **Статус:** Adopt.

- **Описание:** в модели должны быть описаны technical capability с полями `code` и `parents`.
- **Успех:** найдены capability-компоненты с полным описанием.
- **Неуспех:** описанных TC в Structurizr нет.
- **Доступность:** агрегированный прогон.

### CPB.04 — Позиционирование в ФДМ корректно

- **Статус:** Adopt.

- **Описание:** TC не должны быть спозиционированы в группах `dmn.*` или `grp.*` — это неверное позиционирование в ФДМ.
- **Успех:** у всех TC корректные родительские группы.
- **Неуспех:** хотя бы одна TC имеет родителей `dmn.*` или `grp.*`.
- **Доступность:** агрегированный прогон.

### CPB.05 — Качество описания TC в ФДМ соответствует методике

- **Статус:** Adopt.

- **Описание:** оценка качества описания TC по данным БД BeeAtlas (критерий 101). Проверка не пройдена, если есть TC с оценкой 0–2.
- **Зависимости:** переменные окружения `FDMDB_SERVER`, `FDMDB_DB`, `FDMDB_USERNAME`, `FDMDB_PASS`.
- **Успех:** нет TC с оценкой 0–2.
- **Неуспех:** есть TC с оценкой 0–2.
- **Доступность:** агрегированный прогон.

## 4. Технологии

### TECH.01 — Все технологии продукта есть в техрадаре

- **Статус:** Adopt.

- **Описание:** все технологии контейнеров и связей должны присутствовать в техрадаре.
- **Успех:** все технологии найдены в техрадаре.
- **Неуспех:** есть технологии, отсутствующие в техрадаре.
- **Доступность:** агрегированный прогон, отдельный эндпоинт `/api/v1/ff/tech01`.

### TECH.02 — В продукте нет технологий в статусе HOLD

- **Статус:** Adopt.

- **Описание:** не допускается использование технологий со статусом HOLD в техрадаре.
- **Успех:** нет технологий в статусе HOLD.
- **Неуспех:** обнаружены технологии в статусе HOLD.
- **Доступность:** агрегированный прогон, отдельный эндпоинт `/api/v1/ff/tech02`.

### TECH.03 — У всех контейнеров есть технологии

- **Статус:** Adopt.

- **Описание:** у каждого контейнера (кроме пришедших из ландшафта) должно быть указано поле `technology`.
- **Успех:** у всех контейнеров указана технология.
- **Неуспех:** есть контейнеры без технологии.
- **Доступность:** агрегированный прогон, отдельный эндпоинт `/api/v1/ff/tech03`.

### TECH.04 — Приложение не использует протоколы в статусе HOLD

- **Статус:** Adopt.

- **Описание:** связи между контейнерами не должны использовать протоколы в статусе HOLD.
- **Успех:** нет связей с протоколами в статусе HOLD.
- **Неуспех:** есть связи с протоколами в статусе HOLD.
- **Доступность:** агрегированный прогон, отдельный эндпоинт `/api/v1/ff/tech04`.

### TECH.05 — У всех взаимодействий протоколы из техрадара

- **Статус:** Adopt.

- **Описание:** технологии взаимодействия (протоколы) должны быть из техрадара.
- **Успех:** все протоколы связей есть в техрадаре.
- **Неуспех:** есть взаимодействия с протоколами не из техрадара.
- **Доступность:** агрегированный прогон, отдельный эндпоинт `/api/v1/ff/tech05`.

### TECH.06 — Технологии из мониторинга и Git описаны в архитектуре

- **Статус:** Adopt.

- **Описание:** технологии, обнаруженные мониторингом продуктивной среды и GitLab, должны быть отражены в архитектурной модели.
- **Исключения:** HTML, CSS, SSH 2.0, Docker, Alpine Linux, HCL, Groovy, Jinja, Prometheus.
- **Успех:** нет расхождений между мониторингом и архитектурой.
- **Неуспех:** есть технологии из мониторинга, не описанные в архитектуре.
- **Доступность:** агрегированный прогон, отдельный эндпоинт `/api/v1/ff/tech06`.

## 5. Динамические диаграммы

### SQ.01 — Для всех TC указаны sequence-диаграммы

- **Статус:** Adopt.

- **Описание:** для каждой технической возможности должна быть динамическая диаграмма (dynamic view).
- **Успех:** для всех TC найдены соответствующие sequence-диаграммы.
- **Неуспех:** есть TC без sequence-диаграмм, либо TC не определены.
- **Доступность:** агрегированный прогон, отдельный эндпоинт `/api/v1/ff/sq01`.

### SQ.02 — Все вызовы содержат HTTP-запросы

- **Статус:** Adopt.

- **Описание:** в sequence-диаграммах вызовы с REST-технологиями (HTTP/HTTPS/REST) должны иметь описание в формате `GET/POST/PUT/DELETE/PATCH ...`.
- **Успех:** все HTTP-вызовы имеют корректный формат.
- **Неуспех:** есть REST-вызовы без корректного HTTP-метода и пути.
- **Детали:** по строке на вызов — `code` (код TC), `step` (номер шага), `call` (распознанный вызов `МЕТОД ПУТЬ`), `caller_cmdb` / `callee_cmdb` (CMDB вызывающего и вызываемого продукта), `check` (`true` — корректный вызов, `false` — нарушение), `name` (связь, описание, технология), `status`.
- **Доступность:** агрегированный прогон, отдельный эндпоинт `/api/v1/ff/sq02`.

## 6. Диаграммы развёртывания

### DEP.01 — Есть хотя бы одно Deployment Environment

- **Статус:** Adopt.

- **Описание:** в модели должны быть deployment-узлы с указанием окружения (`environment`).
- **Успех:** найдено хотя бы одно окружение развёртывания.
- **Неуспех:** окружений нет.
- **Доступность:** агрегированный прогон.

### DEP.02 — Есть хотя бы одна диаграмма развёртывания

- **Статус:** Adopt.

- **Описание:** должна быть хотя бы одна deployment view.
- **Успех:** найдена хотя бы одна диаграмма развёртывания.
- **Неуспех:** диаграмм развёртывания нет.
- **Доступность:** агрегированный прогон.

### DEP.03 — Окружение развёртывания соответствует CMDB

- **Статус:** Adopt.

- **Описание:** узлы развёртывания (VM, k8s namespace) должны соответствовать данным CMDB (через `get_product_infra`).
- **Успех:** все узлы найдены в CMDB.
- **Неуспех:** есть узлы, не найденные в CMDB.
- **Доступность:** агрегированный прогон.

### DEP.04 — Макросегментация задана правильно

- **Статус:** Adopt.
- **Реализация:** заглушка, логика не реализована. Доступна только отдельным эндпоинтом, в агрегат не входит.

## 7. Контейнерная модель

### CNT.01 — В модели есть контейнеры системы

- **Статус:** Adopt.

- **Описание:** у целевой системы должны быть контейнеры.
- **Успех:** найдены контейнеры.
- **Неуспех:** система не содержит контейнеров.
- **Доступность:** агрегированный прогон.

### CNT.02 — Есть хотя бы одна диаграмма контейнеров

- **Статус:** Adopt.

- **Описание:** должна быть хотя бы одна container view для системы.
- **Успех:** найдена контейнерная диаграмма.
- **Неуспех:** контейнерной диаграммы нет.
- **Доступность:** агрегированный прогон.

### GIT.01 — В модели есть git-репозиторий

- **Статус:** Adopt.

- **Описание:** контейнеры (кроме инфраструктурных и внешних) должны иметь URL с `git`, `nexus` или `harbor`.
- **Успех:** у всех прикладных контейнеров есть репозиторий.
- **Неуспех:** есть контейнеры без репозитория.
- **Доступность:** агрегированный прогон, отдельный эндпоинт `/api/v1/ff/git01`.

### PG.01 — PostgreSQL у критичного приложения (триггер)

- **Статус:** Trial.

- **Описание:** выявляет критичные приложения, использующие PostgreSQL. Критичность должна быть в диапазоне 0–3 (`CL_0` / `MC_1` / `BC_2` / `BO_3`, названия «0-Core» … «3-Business Operation»), а среди технологий продукта должна встречаться подстрока `postgresql` без учёта регистра.
- **Источники:** карточка продукта BeeAtlas `GET /product/api/v2/product/{productCode}/info` — поля `critical` и `techProducts[].tech.label`. Workspace и `docId` не нужны.
- **Детали:** при успехе — технологии PostgreSQL (`code` = id технологии, `name` / `technology` = label, `status: OK`, `check: true`); иначе одна строка `PG.01` со `status: FAIL`.
- **Ошибки:** при недоступности Products API — `isCheck: false` с причиной «Не удалось получить данные продукта».
- **Доступность:** только отдельный эндпоинт `POST /api/v1/ff/pg01`, **синхронный** (`method_synchronous = true`), в агрегат не входит.

## 8. Архитектурные решения

### ADR.01 — Есть хотя бы одно ADR

- **Статус:** Adopt.

- **Описание:** в документации модели должны быть Architecture Decision Records (`documentation.decisions`).
- **Успех:** найден хотя бы один ADR.
- **Неуспех:** ADR не найдены.
- **Доступность:** агрегированный прогон.

### ADR-02 — ADR реализуют назначенные НФТ (LLM-проверка, триггер)

- **Статус:** Trial.

- **Описание:** для каждого ADR корпоративная LLM получает сам ADR и все назначенные продукту НФТ и паттерны, определяет, какие НФТ реализует ADR, и описывает реализацию.
- **Источники:** ADR — `documentation.decisions`; НФТ и паттерны — `GET /product/api/v1/nfr/product?alias={productCode}&branch=main` (только назначенные продукту, ручные и автоматические).
- **Детали:** одна строка на реализованную пару ADR–НФТ — `adr_code`, `adr_name`, `nfr_code`, `nfr_name`, `check: "True"`, `implementation`. ADR без найденных связей в детали не попадают.
- **Результат:** `isCheck: true`, если найдена хотя бы одна пара ADR–НФТ; `false` — если пар нет, а также если нет ADR или назначенных НФТ.
- **Режим:** **асинхронный**. Первый `POST` сразу получает `202`, результат приходит колбэком `POST {FF_MANAGER_URL}/api/v1/ff/webhook` с тем же `callId`. Число параллельных запросов к LLM ограничено `ADR02_CONCURRENCY`.
- **Ошибки:** нет `docId` → `501`; документ не найден → `404`; не настроены LLM или URL FF Manager → `503` с деталями; сбой LLM в фоне → `isCheck: false` с причиной.
- **Доступность:** только отдельный эндпоинт `POST /api/v1/ff/adr02`, в агрегат не входит.

## 9. API и SLA

### API.01 — У приложения есть опубликованные API

- **Статус:** Adopt.

- **Описание:** у приложения должны быть API-интерфейсы с методами (из спецификаций OpenAPI / WSDL / Proto).
- **Примечание:** при локальных спецификациях проверки API пропускаются.
- **Успех:** найдены интерфейсы с методами.
- **Неуспех:** нет ни одного API.
- **Доступность:** агрегированный прогон.

### API.02 — Для части методов определён SLA

- **Статус:** Adopt.

- **Описание:** хотя бы для части методов API должны быть заданы SLA (`rps`, `latency`, `error_rate`) через properties или интеграцию.
- **Успех:** найден хотя бы один метод с SLA.
- **Неуспех:** SLA не определён ни для одного метода.
- **Доступность:** агрегированный прогон.

## 10. Customer Journey

Проверки CX.01 и CX.03 доступны только отдельными эндпоинтами и в агрегат не входят. CX.01 выполняется **по модели** (`model.people`, `model.softwareSystems[].containers[]`), а не по диаграммам. CX.03 работает по внешним API и модель не использует.

### CX.01 — Пользователь взаимодействует с системой (триггер)

- **Статус:** Trial.

- **Описание:** существует Person со связью (в любом направлении) с целевой системой или её контейнерами.
- **Успех:** есть хотя бы один такой пользователь (строка на Person).
- **Неуспех:** пользователей со связью нет, либо система не найдена по `productCode`.

### CX.03 — Customer Journey на BPMN, не черновик

- **Статус:** Trial.

- **Описание:** у приложения есть Customer Journey, построенный на BPMN и не являющийся черновиком. Проверка идёт по внешним API: `GET /product/api/v1/product/{code}` даёт `id` продукта, затем `GET /cx/api/cx/v1/product/cj?idProduct={id}&sample=ALL` — список CJ.
- **Успех:** есть хотя бы один CJ с `bpmn = true` и `draft = false`.
- **Детали:** по строке на каждый найденный CJ — `code` (`uniqueIdent`), `publicationStatus` («Опубликован» / «Черновик»), `journeyType` («BPMN» / «BeeAtlas»). Неподходящие CJ остаются в ответе со `check: false`.
- **Неуспех:** нет ни одного подходящего CJ (все черновики или не из BPMN), CJ нет вовсе, либо продукт не найден.
- **Примечание:** `docId` принимается для совместимости с контрактом, но не используется — workspace в проверке не участвует.
