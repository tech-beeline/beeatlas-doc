#### Назначение

* Контейнер — это абстракция уровня «приложения» или «под-системы» общего приложения.
* Обычно она ориентирована на решение задач одного домена (bounded context) и является независимой единицей развертывания.
* В качестве контейнеров могут выступать сервера бизнес-логики, базы данных, брокеры сообщений, веб-сервера.
* Диаграмма показывает основные технологические решения и то, как контейнеры взаимодействуют друг с другом. 

#### На какие вопросы должна отвечать

* На какие части разделяется приложение?
* Как разделяются зоны ответственности контейнеров в реализации функций приложения?
* Как контейнеры взаимодействуют друг с другом?
* Какие технологии используются при взаимодействии контейнеров?
* Какие данные передаются между контейнерами?

#### Описание контейнера в модели

Пример описания контейнера

```java
capability_service = container "doc_service"" {
    # тэг, для отображения иконки технологии из корпоративного стиля
    tags "java"

    # url gitlab репозитория исходного кода контейнера 
    url "https://git.example.ru/products/eafdmmart/document-service"

    # технология из техрадара компании
    technology "Spring, Java 17"

    # имя для вызова контейнера из вне (будет доступно в landscape)
    # external_name не должно совпадать с именем переменной ( capability_service != ext_capability_service)
    properties {
        external_name ext_capability_service
    }
}
```

!!! info "Чек-лист самопроверки"

    - [ ] Диаграмма должна быть выполнена в нотации C4 уровня C2 [container view](https://docs.structurizr.com/dsl/language#container-view)
    - [ ] Диаграмма должна быть загружена в центральный репозиторий
    - [ ] Все связи должны быть подписаны (иметь заполненный Description)
    - [ ] Для каждого контейнера должен быть заполнен url **путем к исходному коду контейнера на корпоративном gitlab**
    - [ ] Для каждого контейнера должно быть указано имя.
      * В случае если контейнер соответствует **запускаемому сервису** - то имя контейнера должно совпадать с именем сервиса
      * В случае если контейнер соответствует **базе данных** - то имя должно совпадать с именем базы данных (для некоторых субд - имени схемы)
      * В случае если контейнер соответствует **топику/очереди** - то имя должно совпадать с именем топика/очереди
    - [ ] Связи должны идти в направлении вызова
    - [ ] Связи между системами должны иметь указанные протоколы из Техрадара компании  и порты передачи данных. Например, "HTTPS:443" (допускается описание нескольких протоколов через запятую " GRPC, HTTPS:443").
    - [ ] У контейнеров должны быть указаны технологии (**technology**) из Техрадара компании
    - [ ] Отдельные схемы реляционных баз данных должны быть указаны в виде отдельных контейнеров
    - [ ] Отдельные topic kafka должны быть указаны в виде отдельных контейнеров
