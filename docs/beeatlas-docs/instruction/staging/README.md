# Staging Service

## Обзор

**Staging Service** — конфигурируемый ETL-пайплайн, который периодически забирает архитектурные данные из внешних источников (Sparx EA, Structurizr), приводит их к единой канонической модели (продукты/контейнеры/интерфейсы/операции/сценарии) и часть из них публикует в другие сервисы FDM.

Поддерживаются пять типов артефактов:

| Тип | Источник | Публикация |
|---|---|---|
| **[structurizr-sequence](structurizr.md)** | C4-модель продукта и Dynamic Views из workspace.json Structurizr | нет (canonical-модель остаётся в staging) |
| **[e2e-sequence](sparx.md)** | диаграммы последовательностей из Sparx EA | fdm-products |
| **e2e-plantuml** | PlantUML-диаграммы E2E-сценариев | fdm-products |
| **metric-queries** | запросы метрик | dashboard-service |
| **usecase** | Use Case проектов | project-backend |

Набор стадий у каждого типа свой: например, у e2e-sequence и structurizr-sequence есть `pre-adapter` (поиск сценариев в источнике), у e2e-plantuml его нет — сценарий приходит готовым файлом.

## Общий принцип

Все типы проходят один и тот же набор стадий (состав зависит от типа):

```
pre-adapter → adapter → validator → transformer → saver → manual → publisher
```

- **pre-adapter** — находит список артефактов в источнике (какие продукты/сценарии вообще нужно забрать);
- **adapter** — скачивает сырые данные одного артефакта и кладёт их в `staging.raw_data_refs` (с дедупом по хешу содержимого — если с прошлого раза ничего не изменилось, новая строка не создаётся);
- **validator** — проверяет сырые данные на структурную и бизнес-корректность;
- **transformer** — превращает сырые данные в канонический снимок сущностей;
- **saver** — сохраняет снимок в канонические таблицы;
- **manual** — пауза для решения человека: запуск переходит в статус «Ожидает проверки», администратор подтверждает или отклоняет результат;
- **publisher** — публикует принятый результат во внешний сервис (у structurizr-sequence публикации нет — стадия ничего не делает).

Конвейер реализован внутрисервисными исполнителями стадий (`PipelineExecutionService` и набор `ArtifactPipelineStage`): один запуск на конфигурацию × момент времени, артефакты внутри запуска обрабатываются последовательно. Отдельного BPMN-движка (Camunda) в сервисе больше нет.
