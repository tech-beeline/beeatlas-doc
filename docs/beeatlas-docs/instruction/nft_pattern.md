# Работа с нефункциональными требованиями (НФТ) и паттернами
## 1. Нефункциональное требование (НФТ)

### Определение

**Нефункциональное требование (НФТ)** — это корпоративный архитектурный артефакт производственного процесса, определяющий качественные характеристики систем: производительность, надёжность, безопасность, масштабируемость и другие аспекты, описывающие как система должна работать, а не что она должна делать.

НФТ формулируется на уровне корпоративного стандарта и является общим для всех участников производственного процесса, а также может быть назначено на конкретное приложение ручным способом или автоматической проверкой (подробнее ниже).

![nft_ff_livestituatuin.png](..%2Fimages%2Fnft_ff_livestituatuin.png)

### Зачем фиксировать НФТ на корпоративном уровне?

- **Формализовать ожидания** от качества систем в измеримых критериях — стандарт качества задаётся централизованно
- **Автоматизировать проверку** соответствия архитектуры стандартам через привязку к паттернам и фитнес-функциям
- **Обеспечить переиспользование** — одно НФТ, утверждённое на уровне требований производственного процесса, применяется к множеству приложений
- **Отслеживать статус реализации** — система автоматически определяет, выполнено ли требование в контексте конкретного приложения

**Жизненная ситуация** —это группирующая сущность, которая объединяет связанные нефункциональные требования по определённой теме или контексту.

3. Вы попадёте на страницу создания НФТ

## 2. Паттерны

### Определение

**Паттерн** — это проверенное архитектурное решение типовой задачи, которое можно переиспользовать в разных проектах. **Антипаттерн** — это описание типичной ошибки, которой следует избегать.

Паттерн содержит **правило идентификации** — запрос на языке Cypher к архитектурному графу (Neo4j), который автоматически определяет, выполнен ли паттерн в контексте конкретного приложения.

### Как работает проверка паттерна

Паттерн проверяется через правило идентификации — специальный Cypher-запрос к архитектурному графу (Neo4j):

- **Если запрос возвращает результат** — паттерн **выполнен**
- **Если запрос ничего не возвращает** — паттерн **не выполнен**

В правиле идентификации используется подстановка `{ cmdb }` — при проверке она автоматически заменяется на CMDB-мнемонику конкретного приложения (например, `ARFIX`, `LCR` и т.д.).
Реализация паттерна приложением, проверяется в шаге пайплайна публикации новой версии архитектуры.

#### Шаг 3. Правило идентификации

![pattern-step3.png](..%2Fmodels%2Fimages%2Fpattern-step3.png)

**За что отвечает эта страница:** ввод запроса для автоматической проверки паттерна в архитектуре приложения.

| Элемент | Описание |
|---|---|
| **Информационный баннер** | Подсказка: шаг можно пропустить и вернуться позже |

| **Ошибка валидации** | Красное уведомление с описанием ошибки |

**Правила написания запроса:**

1. Используйте `{ cmdb }` для подстановки CMDB-мнемоники приложения
2. Разбивайте сложные запросы на простые и объединяйте через `UNION ALL`
3. Запрос должен быть построен таким образом, что возвращается объект, подходящий под реализацию паттерна. Если запрос возвращает хотя бы одну строку — паттерн выполнен; если ничего не возвращает — не выполнен

**Валидация при сохранении:**
- Запрос проверяется на корректность синтаксиса
- Запрос должен быть **только на чтение** (не модифицировать данные)
- При ошибке отображается описание проблемы

> Этот шаг **можно пропустить** — оставить поле пустым и нажать «Далее». К написанию правила можно вернуться позже при редактировании паттерна.

**Пример правила идентификации (паттерн «БД только во внутреннем сегменте»):**

> Экземпляры СУБД размещаются в изолированном сетевом контуре (private subnet / внутренняя VLAN / закрытый namespace), без публичных IP и без правил межсетевого экрана, разрешающих входящие подключения к портам СУБД из внешних сегментов. Доступ к данным осуществляется только через прикладные сервисы из доверенных зон.

```cypher
WITH 1 AS _ WHERE NOT EXISTS {
  MATCH (ss:SoftwareSystem)-[:Child]->(c:Container)-[:Deploy]->(ci:ContainerInstance)<-[:Child]-(dn:DeploymentNode)
  WHERE toLower(toString(ss.cmdb)) = '{ cmdb }'
    AND ((c.technology CONTAINS 'PostgreSQL') OR (c.technology CONTAINS 'MySQL'))
    AND ((dn.external_ip IS NOT NULL AND trim(toString(dn.external_ip)) <> '')
      OR (dn.host IS NOT NULL AND toLower(toString(dn.host)) CONTAINS 'beeline.ru')
      OR (dn.ip IS NOT NULL AND NOT split(toString(dn.ip), '.')[0] IN ['10', '100', '172', '192']))
} RETURN 1;
```

- Запрос ищет базы данных (PostgreSQL/MySQL), развёрнутые на узлах с внешними IP-адресами
- Если такие узлы **не найдены** (`NOT EXISTS`) — запрос вернёт `1`, и паттерн считается **выполненным** 
- Если узлы найдены — запрос ничего не вернёт, паттерн **не выполнен**

#### Шаг 4. Описание архитектуры в Structurizr DSL

![pattern-step4.png](..%2Fmodels%2Fimages%2Fpattern-step4.png)

**За что отвечает эта страница:** ввод или загрузка описания архитектуры паттерна на языке Structurizr DSL. Описание визуализирует архитектурное решение.

Доступны **два варианта** ввода (взаимоисключающие):

**Предпросмотр:**
- Загруженный файл отображается как отформатированный текст с блоками кода
