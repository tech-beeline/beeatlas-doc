# Синхронная HTTP-проверка

Синхронная проверка вызывает ваш сервис по URL из поля **`method`** тем же **POST**, что и асинхронная, но **результат ожидается в теле HTTP-ответа** этого вызова. Запись в **`product_ff`** выполняется сразу (логика совпадает с **`POST /api/v1/ff/webhook`**). В ответе **`POST /api/v1/run/{code}`** поле **`check_result`** содержит **`is_check`** из ответа сервиса.

## Когда выбрать этот режим

- Результат известен до завершения обработки запроса.
- Не нужен отдельный колбэк на webhook.

## Настройка в БД (признак режима)

- В таблице **`ff.fitness_function`**: непустой **`method`**, **`method_synchronous = true`**.

## Создание проверки через API

**`PUT /api/v1/fitness-function/{code}`** (`multipart/form-data`):

| Поле | Значение |
|------|----------|
| `description` | Описание |
| `method` | Полный URL (**POST**), куда FF Manager отправляет JSON |
| `method_synchronous` | **`true`** (или `1`, `yes`, `on` — см. обработку формы в сервисе) |

## Что отправляет FF Manager на ваш URL

Поведение запуска такое же, как у асинхронной проверки:

- **HTTP:** `POST`, `Content-Type: application/json; charset=utf-8`
- **Тело:**

```json
{
  "callId": "<uuid>",
  "productCode": "<мнемоника из поля app в run>",
  "branch": "<ветка продукта; по умолчанию main>"
}
```

### Параметр `docId`

Если при **`POST /api/v1/run/{code}`** или **`POST /api/v1/run-all`** в query указан **`docId`**, к URL из **`method`** добавляется **`docId=...`** (без изменения JSON-тела). Это работает и для синхронного, и для асинхронного режима.

### Параметр `branch`

Запуск считается для ветки продукта, переданной в query **`branch`** (по умолчанию **`main`**). Эта же ветка уходит в исходящий запрос полем **`branch`**; правила **`applicability`** считаются по ней же.

## Ожидаемый ответ вашего сервиса (обязательно)

- Статус **2xx**.
- **Тело ответа — JSON-объект**, по смыслу как тело **`POST /api/v1/ff/webhook`**:

| Поле | Обязательность | Описание |
|------|----------------|----------|
| `callId` или `call_id` | Да | Должен **совпадать** с **`callId`**, который FF Manager отправил в запросе |
| `isCheck` или `is_check` | Да | Boolean — прошла ли проверка |
| `details` или `json_details` | Нет | Детали (строка, объект или массив) |
| `countDetail` / `count_detail`, `successDetail` / `success_detail` | Нет | Целые числа, если нужны |

Если **`callId`** в ответе не совпадает с исходящим, JSON невалиден, нет **`isCheck`**, или **`isCheck`** не boolean — вызов считается ошибкой, ожидающая запись вызова удаляется, **`run`** вернёт ошибку.

Таймаут запроса к вашему URL: **`FF_EXTERNAL_FF_TIMEOUT_SECONDS`**.

## Что происходит после успешного ответа

1. Результат записывается в **`product_ff`** (как при webhook) — кроме проверок со статусом **TEST**: для них результат возвращается только в **`check_result`** и в **`product_ff`** не сохраняется.
2. Контекст вызова в **`outside_ff`** помечается завершённым.
3. Клиент **`run`** получает **`check_result`**: значение **`is_check`** из JSON-ответа.

## Запуск проверки

- **`POST /api/v1/run/{code}`** — `{"app": "<мнемоника>"}`; опционально **`?docId=...`**, **`?branch=...`**, **`?source_type=...`**, **`?source_id=...`**
- **`POST /api/v1/run-all`** — аналогично; проверки со статусом **TEST** в run-all не участвуют

Учитываются правила **`applicability`** (не для **TEST**; **TRIAL**/**ADOPT** — как боевая проверка).

### Формат ответа

У каждой проверки в ответе есть **`code`** и **`name`**: `name` берётся из **`fitness_function.description`** и равен **`null`**, если записи в БД нет или описание пустое.

**`POST /api/v1/run/{code}`** — объект:

| Поле | Описание |
|------|----------|
| `code`, `name` | Код и название проверки |
| `app`, `branch` | Мнемоника продукта и ветка расчёта |
| `success` | `true`, если проверка выполнена без ошибки |
| `message` | Сообщение об ошибке расчёта (при `success = false` запрос вернёт **400**) |
| `check_result` | Детали: `is_check`, `details`, `countDetail`, `successDetail`; для асинхронной проверки — `null` или `{ "pending": true, "callId": "..." }` |
| `status` | Статус проверки (**TEST** / **TRIAL** / **ADOPT**), если запись есть в БД |
| `method_synchronous` | Признак режима, если у проверки задан `method` |

**`POST /api/v1/run-all`** — `{ app, branch, results, skipped }`, где **`results`** — объект с ключом-кодом проверки, а значение — те же поля (`code`, `name`, `success`, `message`, `check_result`, `status`). В **`skipped`** — проверки, которые не запускались, с полями `code`, `name`, `reason`.

### Расчёт по workspace без сохранения: `POST /api/v1/run-all-workspace`

Проверяет продукт по **workspace.json из тела запроса**, не сохраняя результаты:

- тело запроса — сам JSON-документ workspace Structurizr (то же, что отдаёт Structurizr по `/json`), без обёртки;
- query: **`app`** (обязательно) — мнемоника продукта, **`branch`** — ветка (по умолчанию `main`);
- сервис сам создаёт документ в Documents API и передаёт его `docId` синхронным внешним проверкам, а скриптам — workspace в `data`;
- запускаются проверки со статусом **TRIAL** и **ADOPT** (TEST исключаются), applicability считается по актуальным `product_ff` и по успешным результатам этого же вызова;
- асинхронные внешние проверки (`method_synchronous = false`) не запускаются и попадают в **`skipped`**;
- ничего не записывается: ни **`product_ff`**, ни **`outside_ff`**; скрипты без `execute()` в этом режиме не запускаются;
- максимальный размер тела — **16 МиБ**, иначе **413**; пустой **`app`** — **400**, ошибка получения ключей Structurizr или создания документа — **502**.

Ответ: `{ app, branch, docId, results, skipped }` (и `message`, если не запущено ни одной проверки).

- **`results`** — объект, ключ — код проверки; значение: `code`, `name`, `success`, `message`, `check_result`, `status`;
- **`skipped`** — массив `{ code, name, reason }`; причины: асинхронная внешняя проверка не запускается в режиме без сохранения, не выполнены условия `applicability` (нет актуальных `product_ff` с `is_check = true`), проверка со статусом **TEST** не входит в расчёт.

```json
{
  "app": "FDMSHOWCASEAPP",
  "branch": "main",
  "docId": 57353,
  "results": {
    "API.01": {
      "code": "API.01",
      "name": "Наличие опубликованных API",
      "success": true,
      "message": "",
      "check_result": { "is_check": true, "countDetail": 49, "successDetail": 49 },
      "status": "ADOPT"
    }
  },
  "skipped": [
    { "code": "<код проверки>", "name": "<название проверки>", "reason": "асинхронная внешняя проверка (method_synchronous=false) не запускается в режиме без сохранения результата" }
  ]
}
```

## Сравнение с асинхронной HTTP-проверкой

| | Синхронная | Асинхронная |
|---|------------|-------------|
| **`method_synchronous`** | `true` | `false` |
| Результат | В **теле ответа** на первый POST | Через отдельный **`POST /api/v1/ff/webhook`** |
| **`check_result` в ответе `run`** | Обычно задан (`is_check`) | Обычно **`null`** до webhook |

Подробности исходящего запроса и **`docId`**: см. также **`docs/http-check-async.md`**.
